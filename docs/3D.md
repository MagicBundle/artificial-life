## 1. Goals and non-goals

**Goals.**
- Agents live in a water-column-like volume. Life near the floor is cheap; climbing against gravity costs
  energy.
- Food is distributed by depth (a benthic band at the floor and an optional photic band near the surface), so
  vertical niches can form.
- Corpses sink. This sets up a downward nutrient flow ("marine snow").
- Bonded structures can take real 3D shapes. This is the main scientific payoff: the 2D run never sustained
  bodies (RESEARCH.md P2).
- Every existing guarantee carries over:
  - the exact 16-term energy ledger;
  - determinism per backend;
  - replay;
  - the director's safety rules and log.

**Non-goals for v1.** No fluid dynamics, no terrain, no 3D bodies with rotation coupling (bonds stay
point-to-point springs), and no 2D↔3D genome transfer. (A buoyancy actuator was a non-goal in the first draft; the
owner chose one on 2026-10-13, §11 Q3.)

## 2. Coordinates and boundaries

- `pos` has shape (N,3) as (x, y, z). x and y are periodic on `[0, L)` as now; z lies in `[r, height − r]`.
- Validation requires `2·height ≤ L`, so every `|dz| < L/2` and `ops.min_image` is exactly the identity on z: it
  applies to 3-vectors unchanged. Positions wrap in x and y and clamp in z through a new helper (`ops.wrap` stays
  elementwise; wrapping z would put −0.3 at L − 0.3). The clamp is the floor and surface contact. The agent moves
  to the boundary and its stored inward velocity is zeroed; `Counter3D` counts floor clamps, surface clamps and
  grounded agents (§12 Q7).
- **Grounded:** `z ≤ r + floor_eps`, at the floor only (the surface grants no grounding, §11 Q2). Grip applies
  its drag factor to horizontal motion only when grounded and never slows sinking (§12 Q14). Harvest is not gated
  on grounding: the benthic band is the floor layer, which grounded agents always occupy (§12 Q9).
- **Gravity:** a constant force `−physics.gravity · ẑ` on every survivor (overdamped, so sinking speed is
  `g/γ`). It must satisfy `gravity < thrust_max·sin(φ_max)` so agents can climb at full pitch. Hovering by thrust
  then costs about `move_cost·(g/(thrust_max·sin φ_max))²` per step through the existing movement cost. Gravity
  itself has no ledger term: it does no bookkeeping work in an overdamped model.
- **Buoyancy** (§11 Q3): an upward force `b·ẑ`, `b = cap·max(tanh y, 0)` from `OUT_BUOYANCY`, with the
  heritable cap `cap = buoy_cap·physics.buoyancy_max`. Its cost is booked in `HEAT_BUOYANCY`.

## 3. Orientation and the brain's frame

- **Representation:** yaw θ (the existing `heading`) plus a new `pitch` φ, clamped to `[−φ_max, φ_max]` with
  `φ_max = 80°`. Gravity defines "up", so roll is unnecessary. Yaw/pitch has no float drift (a quaternion
  needs renormalising) and no gimbal problem inside the clamp.
- **Body frame:**
  - `fwd = (cos φ cos θ, cos φ sin θ, sin φ)`;
  - `lat = (−sin θ, cos θ, 0)`;
  - `up = fwd × lat`.

  `ops.to_body` gains a 3D variant returning (fwd, lat, up) components. The lateral axis stays horizontal,
  which keeps sensing intuitive under gravity.
- **Outputs:** `OUT_TURN` stays yaw; a new `OUT_PITCH` changes φ by up to `turn_max`. The turn cost becomes
  `turn_cost·(|turn| + |pitch|)/turn_max`, a cost change only with no new ledger term. `OUT_BUOYANCY` drives the
  buoyancy force (§2).

## 4. Genome layout for dims = 3

`layout.for_dims(nd)` gives the layout per dims (built in PR 1, DESIGN §27.1). The 2D module constants are
unchanged, and the genome layout version is per dims (2D stays 1; 3D is `GENOME_LAYOUT_VERSION_3D = 2`).

The layout is **append-only** (§12 Q1): the 3D vectors are the 2D vectors unchanged, followed by a 3D-only tail.
Every 2D index keeps its value and meaning in 3D, so no 2D column can silently be read as a 3D one, and only
`D_IN`, `D_OUT`, the descriptor width `NF` (7 → 8), the query width `F` (6 → 7) and the version depend on dims.
An earlier draft grouped the z components into each block, which shifted every index after `IN_VEL`.

| tail | index | content |
|---|---|---|
| `IN_VEL_UP` | 69 | body-frame up component of `vel / v_max` |
| `IN_RES_GRAD_UP` | 70 | resource gradient, up |
| `IN_CHEM_GRAD_UP` | 71–73 | chemical gradients, up (NCH wide) |
| `IN_NBR_DZ` | 74–76 | up offset / R of the NS nearest neighbours |
| `IN_BOND_DZ` | 77–80 | up offset / `break_length` per bond slot |
| `IN_HEIGHT` | 81 | z / height (named "height", not "depth", §12 Q17) |
| `IN_PITCH` | 82 | sin φ |
| `IN_GROUNDED` | 83 | 1 on the floor, else 0 |
| `OUT_PITCH` | 35 | pitch change `turn_max·tanh(y)` |
| `OUT_BUOYANCY` | 36 | buoyancy fraction `max(tanh(y), 0)` |
| `OUT_Q_BOND_DZ` | 37 | 7th component of the bond query |
| `OUT_Q_ATTACK_DZ` | 38 | 7th component of the attack query |

So D_IN is 84 (69 in 2D) and D_OUT is 39 (35 in 2D). The neighbour descriptor gains `NBR_DZ` as its 8th feature;
the 2D input blocks `IN_NBR` (NS·7) and `IN_BOND` (B·5) keep their widths and the z offsets go to the tail. A query
is the 2D block of six followed by its `*_DZ` component, in the order of the descriptor.

Parameters grow by about 14%: (84 + 32)·32 + 33·39 = 4 999 against 4 387 (founder brain cost about +10%). This
is small next to the neighbour search.

## 5. Fields

- **Lattices:** resource is int32 and chemicals are f32, both with shape (FZ, FG, FG), where `FZ = height /
  field_cell` and `FG = L / field_cell`. Index order is [z, y, x].
- **Integer diffusion:** a 3D twin `ops.int_diffuse_3d` (`int_diffuse` is unchanged) with **no-flux boundaries
  in z** (periodic in x and y). It stays an exact flux stencil, so the total is conserved bit-for-bit, and needs
  `resource_diffusion_q8 ≤ 42` to keep every cell in `[0, R_HARD]` (DESIGN §27.6). Chemical diffusion uses the same
  boundary rule in float (mirrored ghost layers).
- **Fertility:** `clip(fertility_base + Σ_p w_p · gx_p ⊗ gy_p, 0, 1)` as now, multiplied by a **vertical
  profile** `V` by layer index k (§12 Q9), with `V[0] = 1` so the floor layer equals 2D fertility exactly:
  - a benthic band `exp(−k·field_cell/λ_b)`;
  - plus an optional photic band `a_s · exp(−(FZ − 1 − k)·field_cell/λ_s)`, off by default (`photic_amp = 0`,
    §11 Q1).

  Keep it elementwise; no GPU matmul (F20). The (PP, FG, FG) patch term is computed once and broadcast over
  z. Do not materialise (PP, FZ, FG, FG).
- **Corpses sink:** `E + S` is scatter-added into the **floor cell** below the corpse, `(0, cy, cx)`. That
  keeps the same `FLOW_CORPSE` ledger term at a different cell. The scatter lives in `ops.py` (lint rule).
- **Sensing:** the resource and chemical gradients are 3D central differences. At the floor and surface the z
  neighbour index is clamped and the divisor stays 2 (mirroring, consistent with the no-flux diffusion; §12 Q8).
  This is not the same as a one-sided difference, which an earlier draft claimed.

## 6. Neighbour search and placement

- **Hash grid:** `G_xy × G_xy × G_z` cells, with `G_z = floor(height / R)` and z non-periodic. The search covers
  3×3×3 cells (27C candidates instead of 9C), with out-of-range z layers masked. The brute-force kNN equality
  test gets a 3D variant that covers the floor, the surface and x/y seams.
- **Offspring:** placed at `offspring_distance` in a ±0.5 rad cone behind the parent, reflected vertically when
  the point would leave `[r, height − r]`, so the offset (the child bond's rest length) is kept; with zero jitter
  this is the 2D rule (§12 Q6). A uniform direction plus a z clamp could shorten the offset to 0.
- **Immigrants:** uniform in the volume (§11 Q4).
- **Founders:** uniform in the volume with random yaw and pitch. The 3D draws use the existing RNG streams with
  3D-only shapes, so there is no new stream and no `RNG_LAYOUT_VERSION` bump; the dims = 2 draws are untouched
  (§12 Q4).

## 7. Everything else

- **Bonds and springs:** 3-vector offsets `(N,B,3)`. The forces are already vector-valued and antisymmetric
  per pair; check that the test still holds in 3D.
- **Director levers:** `fertility_shift` in its move form moves patches in x and y only. The vertical profile is
  not a lever in v1. The catastrophe is a vertical column (§12 Q10). The safety rules, budgets, log and replay are
  unchanged.
- **Ledger:** buoyancy costs are booked in `HEAT_BUOYANCY`, the 16th entry (slot 15, `RESERVED` and always 0 in
  2D); the ledger stays 16 terms (§12 Q3).
- **Metrics (dims = 3 only, new keys):**
  - height distribution (mean, quartiles, grounded fraction);
  - mean speed (also deferred for 2D in DESIGN §23.2);
  - vertical niche occupancy per clade;
  - body extent in z.
- **Invariants:**
  - z stays in `[r, height − r]`;
  - pitch stays in `[−φ_max, φ_max]`;
  - the lattice shapes are right;
  - the ledger closes;
  - `full_check` gets 3D branches.
- **Config:**
  - `world.dims` (default 2) and `world.height` (PR 1);
  - `physics.gravity`, `physics.floor_eps`, `physics.buoyancy_max`;
  - `mutation.buoy_init`, `mutation.buoy_sigma` (the cap's additive mutation, like `tag_sigma`);
  - `energy.buoyancy_cost`, `energy.buoyancy_cap_cost`;
  - `fields.benthic_lambda`, `fields.photic_amp`, `fields.photic_lambda`.

  All new keys default to off or 2D and go in `config.POST_V01_KEYS` and `config.THREE_D_KEYS`; in 2D they must
  keep their defaults. dims = 3 changes the compiled step and the layout, so it is hashed when not default.
  Resume or fork across dims is refused with a clear error. New presets are `tiny3d` (PR 3) and `64k3d` (§9).
- **Counters:** `Counter3D` (`Z_FLOOR_CLAMPS`, `Z_SURFACE_CLAMPS`, `GROUNDED`, indices 27–29) is appended to
  `StepOut.counters` in 3D only; `CounterIdx` stays 27 (§12 Q7).
- **CLI:** `inspect` reports dims. `bench` needs 3D branches that mirror the step's (`bench._StagedStep` copies
  the pipeline, PR 3). The 2D MLX `render` and `view` refuse dims = 3 with a pointer to the Swift viewer.

## 8. Viewer (Swift, in AlifeControl)

- **Rendering:** raw Metal through `MTKView`, drawing instanced spheres (or impostor billboards) for agents
  and line segments for bonds, with an orbit and fly camera.
  - RealityKit's high-instance-count path (`LowLevelMesh`) needs macOS 15, and the app targets macOS 14.
  - SceneKit is soft-deprecated.
  - Metal handles 64k+ instances at 60 fps on the M5 Pro.
- **Data path:** a new `alife stream RUN|FILE` command re-simulates from a checkpoint, as `view` does. It
  writes length-prefixed binary frames to stdout:
  - a JSON header (dims, L, height, N, colour mode);
  - per frame: alive mask, pos f32, yaw and pitch f16, colour u32, bond pairs.

  The GUI already launches `.venv/bin/alife` as a `Process`, so it reads the pipe. It never writes into the run
  directory (unlike `view`, which writes snapshots under `media/`). It re-simulates without the director, as
  `view` does, so only a `--follow` mode that reads new checkpoints shows a director run faithfully (§12 Q16).
- **Status (PR 4, built):** the protocol of record is DESIGN §27.11, which PR 5's Swift decoder follows; this
  section is the rationale. The sketch above grew in these ways: a record is a 4-byte tag and a length (so a
  version-1 decoder can skip records of a later version), positions are always 3 floats (a 2D stream has z = 0), a
  frame can carry the RGB colours of one field layer for the slice plane, stdin carries control lines (`pause`,
  `run`, `step [N]`, `every K`, `color MODE`, `fields on|off|z K`, `quit`; EOF = quit), and a closed pipe ends the
  process with exit 0. Fixtures for the decoder tests are `tests/data/stream_tiny_{2d,3d}.bin` with JSON sidecars.
- **Status (PR 5, built):** DESIGN §27.12. The shape is as above, with these particulars:
  - the viewer is a separate `Window("3D Viewer")` of AlifeControl, fed by an `alife stream` process that it starts
    and stops (`quit`, then one SIGTERM after a grace period) with its window and with the app;
  - a dedicated thread drains the binary pipe into the decoder, and the main actor takes the newest frame, so a slow
    window never stalls the engine and a slow engine never stalls the window;
  - agents are ray-traced sphere impostors with a pale nose for the heading, bonds are half segments to the
    minimum-image midpoint, and the planes, the box and the field slice are drawn as described below;
  - "Open 3D viewer" follows the run in progress and re-simulates any other (and says that it ignores the director);
  - the 3D levers are in the main window, diffed against the preset (a fork: its source);
  - the shaders are one string compiled at run time (no resource bundle, no Metal Toolchain);
  - a draw into the window never waits for the GPU on the main thread, and the clip planes follow the pose, so zooming
    out never cuts the world off.
- **Display options:**
  - colour modes as in 2D (tag, energy, clade; there is no "kin" mode);
  - optional translucent floor and surface planes;
  - an optional resource or chemical slice plane at a chosen z;
  - pause, step and speed controls;
  - a snapshot to PNG.
- **Scope:** the viewer also accepts dims = 2 streams (z = 0), so it can later replace pygame for 2D.

## 9. Sizing, performance and tuning

**Starting point: the `64k3d` preset.** (Built in PR 6; DESIGN §27.13 has its values, their derivation and the
measurements. The numbers below are the proposal's: the preset differs in gravity 0.015 (the cloud sweeps and
the owner), `C = 48` (confirmed 2026-10-16; 24 until the cloud run overflowed it, so 1 296 neighbour candidates per
agent, a measured 3.3 GB peak, and 14.4 steps/s on the M5 Pro against the 30 to 40 below, which was for `C = 16`),
`brain_cost_per_l1` 0.0905, `regen_max` 1 700 and `n_init` 16 384 (as derived, not yet tuned), and `K_est` is
occupancy-weighted, not floor-only (the director's extinction-risk test alone reads the floor layer's capacity).)
- `L = 320`, `height = 80`: volume 8.2M, which matches the 2D neighbour density for about 33k agents if they spread
  uniformly. Under gravity they will crowd the floor, so retune.
- `field_cell = 4`, giving an 80×80×20 lattice of 128k cells.
- Sensing radius 6, giving a 53×53×13 hash grid.
- `gravity = 0.03`, so net climbing speed is about 0.07 at full thrust.

**Expected cost.**
- The neighbour search is about 3× (27 vs 9 cells).
- Fields are about 2× (128k vs 65k cells, 7-point stencil).
- The brain is about 1.15× (§4).
- Estimate 30–40 steps/s versus 61 in 2D. Measure with `bench --stages` after PR 3.
- **Measured (2026-10-16, M5 Pro, `bench --stages`, DESIGN §27.13; reports in `docs/bench/`).** 14.4 steps/s at
  `C` = 48 (24.9 at `C` = 24, 22.0 at 32) against 59.3 in 2D, and a 3.3 GB peak (2.2 GB at `C` = 24; the estimate was
  2.8 to 3.5 GB).
  - The estimate holds for `C` = 16 (about 30 steps/s, extrapolated) and not for the `C` the world needs.
  - The 27-cell neighbour search is 56 of the 71 ms of the staged step at `C` = 48 (6.3 of 19 ms in 2D). It costs about
    4.3 ms per 100 candidates per agent in 2D and 3D alike, so it scales with `Q` = 27·`C` (1 296, against 144 in 2D),
    not with the cell count; `C` = 48 triples the candidates of `C` = 16 again.
  - The rest of the step costs 15 ms against 12.9 in 2D, as estimated.
  - The lever is the deferred fused Metal neighbour kernel (DESIGN §23.2 item 1).

**Tuning risk.** This is the highest-risk part. The 2D defaults were tuned for 2D contact rates and diffusion.
In 3D:
- chemical signals dilute as 1/r rather than logarithmically;
- encounters are rarer at the same density;
- gravity concentrates life on the floor.

The 3D variants of `test_affordances` and the slow ecology test must pass before any long run.

## 11. Questions for the owner (answered 2026-10-13)

1. **Vertical food profile.** Floor only (benthic), or floor plus a photic band near the surface? The
   recommendation was both, with the photic band optional, because two food bands separated by a costly water
   column create niches.
   **Answer:** a benthic band plus an optional photic band; `fields.photic_amp` defaults to 0 (off), and the
   `64k3d` preset turns it on.
2. **Surface boundary.** A solid ceiling (clamp, as at the floor) or the same clamp without grounding. The
   recommendation was the clamp without grounding: the surface is not a floor.
   **Answer:** the clamp without grounding. An agent at the surface stops at z = height − r with its upward
   velocity zeroed, and gets neither floor friction nor grounding.
3. **Buoyancy actuator.** None in v1 (thrust only), or a heritable buoyancy trait or output with an energy
   cost. The recommendation was none in v1.
   **Answer:** a brain output with a heritable cap.
   - The output `OUT_BUOYANCY` gives `b = cap·max(tanh y, 0)`, an upward force; zero use is exactly free.
   - The cap is a per-agent trait `buoy_cap ∈ [0, 1]`; the effective cap is `buoy_cap·physics.buoyancy_max`. A
     child inherits it with additive Gaussian noise and a clip (`mutation.buoy_sigma`, like `tag_sigma`), so 0
     is reachable and can be left again.
   - The cost per step is `buoyancy_cost·(b/bmax)² + buoyancy_cap_cost·buoy_cap`: use, plus upkeep of the cap
     even at b = 0. Both are booked in `HEAT_BUOYANCY`, ledger slot 15 (`RESERVED` stays the canonical name and
     is 0 in 2D; `HEAT_BUOYANCY` is an alias, named per dims in metrics).
   - 3D D_OUT is 39 (§4).
4. **Immigrant placement.** Uniform in the volume, or dropped at the surface so they must sink to the floor.
   The recommendation was uniform.
   **Answer:** uniform in the volume.
